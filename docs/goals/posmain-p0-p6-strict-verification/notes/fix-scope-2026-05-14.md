### 2. Moova Direct-Widget Contract Blocker

- Impacted surfaces: `ajax/moova_confirm_order.php`, `ajax/moova_change_order.php`, `classes/Pos/Service/PosOrderMutationService.php`, `classes/Moova/MoovaNewOrderApplyService.php`, `classes/Moova/MoovaChangeOrderApplyService.php`, direct widget response metadata, idempotency, table-state mutation, fulfillment metadata, and sync/outbox writes.
- Current evidence: endpoint source tests fail because the endpoints instantiate `PosOrderMutationService`, while the contract test expects direct endpoint-level instantiation of `MoovaNewOrderApplyService` and `MoovaChangeOrderApplyService`.
- Important nuance: `PosOrderMutationService::confirmMoovaOrder()` currently delegates to `MoovaNewOrderApplyService()->applyInTransaction(...)`, and `PosOrderMutationService::changeMoovaOrder()` delegates to `MoovaChangeOrderApplyService()->applyInTransaction(...)`. So the failing source-contract test may be stale in *where* it expects the service call, not necessarily proof that live direct-widget behavior is broken.
- Compatibility risk: replacing the wrapper path blindly could bypass shared mutation-service events or future hooks; updating only tests/tooling could hide a real architectural requirement if the endpoint-level contract was intentional.
- Smallest safe decision if approved: Judge/owner should decide whether `PosOrderMutationService` is the canonical endpoint facade. If yes, update the contract to assert transitive delegation through the mutation service. If no, restore endpoint-level apply-service calls while preserving all live E2E behavior.
- Verification gate:
  - `php /tmp/posmain-phpunit-9.phar --bootstrap /tmp/posmain-phpunit-autoload.php --colors=never tests/sync/moova_widget_bridge_contract_test.php`
  - live Moova create/confirm, decline, edit, cancel, cancel-after-edit under healthy local Moova runtime
  - Moova payload checks for `syncStatus`, `syncEventType`, idempotency replay, and fulfillment metadata.
