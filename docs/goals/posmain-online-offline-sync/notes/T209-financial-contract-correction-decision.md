# T209 Financial Contract Correction Decision

## Decision

Authorize one bounded local correction. Do not backfill hosted history, redesign the sync engine, enable automatic cloud-to-branch mutation, or deploy in this task.

The correction is limited to the durable POS order contract and the migration targets that currently destroy financial meaning. It keeps branch-to-cloud automatic delivery and guarded manual empty-branch restore unchanged.

## Exact data rules

- Preserve source `NULL` as `NULL`; unknown historical money is not zero.
- Encode header money, payment amounts, receipt amounts, discounts, and line totals at four decimal places.
- Encode quantities, unit price/cost, and line/header profit at six decimal places.
- Keep the certified posted financial bundle at its existing exact two-decimal `Money` boundary.
- Advance the POS order snapshot schema from version 3 to version 4. Existing schema-v1/v2/v3 events remain accepted.

## Migration boundary

- `ot_head.fat_total`: `DECIMAL(19,4) NULL DEFAULT NULL`; no NULL normalization.
- `ot_head.fat_tax`: `DECIMAL(19,4) NULL DEFAULT NULL`; no NULL normalization.
- `ot_head.profit`: `DECIMAL(19,6) NULL DEFAULT NULL`; no NULL normalization.
- `fat_details.profit`: `DECIMAL(19,6) NOT NULL DEFAULT 0.000000`; the hosted audit found no NULL blockers, so no data repair statement is needed for current tenants.
- Keep the existing targets for `pro_value`, `fat_net`, and `discount`; this task does not reinterpret their established semantics.
- Add nullable `fat_tax DECIMAL(19,4)` and `profit DECIMAL(19,6)` to new and existing `cloud_orders` tables.
- Widen `cloud_order_lines.profit` to `DECIMAL(19,6)` and the quantity/price/cost projection columns to `DECIMAL(19,6)` so the durable version-4 payload is not truncated after receipt.

No historical `fat_total`, `fat_tax`, or header `profit` value may be generated by this migration.

## Snapshot, projection, and restore boundary

1. `PosOrderSnapshotBuilder` adds header `fat_tax` and `profit`, emits version 4, preserves NULL, and uses the explicit four/six-decimal policy above.
2. `CloudOrderSnapshotService` projects header tax/profit and six-decimal line measures without converting absent values to zero. The raw event JSON remains the source receipt.
3. `CloudLegacyPosMirrorService` writes header tax/profit during guarded restore and preserves NULL. Line profit is restored at six decimals.
4. Older events that omit the new fields restore those fields as NULL; they are not rejected and do not enable reverse automation.

## Focused proof

The Worker must cover:

- migration SQL contains the nullable header targets and no NULL-to-zero statement for them;
- additive cloud upgrades are emitted for already-created projection tables;
- a source order carrying four-decimal tax and six-decimal profit retains both through snapshot and cloud projection;
- a NULL variant remains NULL through cloud projection and manual restore;
- line profit and quantity/cost precision survive at six decimals;
- schema-v1 restore compatibility, stale-event handling, idempotency, and the financial bundle remain green.
