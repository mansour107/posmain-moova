## Phase 0 Exhaustiveness Rule

The write sweep used these runtime patterns:

- `INSERT INTO fat_details`
- `UPDATE fat_details`
- `DELETE FROM fat_details`
- `UPDATE myitems SET ... itmqty/cost_price/last_price`
- `INSERT INTO inventory_movements`
- `UPDATE inventory_movements`
- `INSERT INTO inventory_item_balances`
- `UPDATE inventory_item_balances`
- destructive new-inventory table operations such as `DELETE FROM inventory_movements`,
  `DELETE FROM inventory_item_balances`, `DELETE FROM stock_reservations`,
  `DELETE FROM inventory_*` workflow tables, `TRUNCATE inventory_*`, and
  `DROP TABLE inventory_*`
- `INSERT INTO stock_reservations`
- `UPDATE stock_reservations`
- repository calls to `createMovement()` and `putBalance()`
- helper writes through `insertRow($conn, 'inventory_movements')`, `insertRow($conn, 'stock_reservations')`, `insertRow($conn, 'production_batches')`, and `insertRow($conn, 'production_batch_lines')`
- reservation ownership through `StockReservationRepository` and `RecipeReservationService`
- production batch ownership through `ProductionBatchService`, `ProductionBatchMutationService`, and `ProductionBatchRepository`
- POS line normalization through `InventoryMovementService::normalizeInvoiceLines()` before legacy `fat_details` inserts
- CLI apply surfaces under `tools/inventory_*.php` that can backfill movements, rebuild balances, repair `myitems.itmqty`, or retire legacy triggers
- recipe CLI stock/fixture apply surfaces that can seed QA balances, post QA stock adjustments, run migrated order-write smoke checks, or create isolated browser fixture `fat_details` rows
- direct stock/catalog SQL inside inventory or recipe CLI tools, including fixture-only `UPDATE myitems`, trigger-retirement `DROP TRIGGER`, isolated fixture `DROP DATABASE`, and direct fixture `fat_details` inserts
- non-inventory/non-recipe CLI tools that can seed or clean stock-like item master rows, including Phase 6 load-check fixtures and demo restaurant seed data
- reservation-expiry apply surface in `tools/recipe_expire_reservations.php`
- guarded destructive admin reset paths with dynamic `DELETE FROM $table` SQL and stock/catalog table names such as `fat_details` or `myitems`
- catalog item creation/import/sync paths with `INSERT INTO myitems` and cost/price/barcode fields, because they do not move stock but create inventory inputs
- unit conversion writers with `INSERT INTO item_units`, `UPDATE item_units`, or `DELETE FROM item_units`, because future sales, purchases, counts, adjustments, transfers, and recipe conversions depend on stable `u_val`
- recipe definition writers with `INSERT/UPDATE recipe_headers`, `INSERT/UPDATE/DELETE recipe_lines`, `DELETE/INSERT recipe_variant_lines`, and `INSERT recipe_cost_snapshots`, because future sale, reservation, production, and cost flows depend on active recipe/BOM truth
- recipe usage and availability cache writers with `insertRow($conn, 'recipe_order_line_usage')`, `UPDATE recipe_order_line_usage`, `INSERT INTO recipe_availability_cache`, and `putAvailability()`, because they are stock-effect evidence/control surfaces even though they do not directly add or subtract on-hand quantity

The contract test excludes `tests/`, `tools/`, `docs/`, `vendor/`, and non-PHP database dump files from the runtime sweep, then requires every matching PHP file to be named in this map. It separately checks inventory CLI tools, recipe CLI stock/fixture tools, other CLI stock/catalog seed tools, and the recipe reservation expiry tool so migration/repair/fixture/smoke/demo apply paths cannot hide outside the runtime page sweep. The contract also names the Inventory module services that now own purchase receiving, transfer, count, adjustment, reservation, production batch, and migration writes, so this map cannot stay green by documenting only legacy writers. Any future phase that changes inventory behavior should rerun the sweep and update this map before changing runtime behavior.

## Selling Items Today

For a normal sale/POS line:

1. The sale flow creates or updates an `ot_head` order header.
2. It inserts a `fat_details` line with `qty_out = sold_qty * u_val` and `qty_in = 0`.
3. The `fat_details` trigger recomputes `myitems.itmqty` from all active details for that item.
4. If the invoice/order is POS and recipe features are enabled, lifecycle hooks can also explode the sellable item recipe and write ingredient consumption to `inventory_movements` plus `inventory_item_balances`.

So selling a burger-like recipe item can affect two different things:

- sellable item legacy stock via `fat_details.qty_out`,
- ingredient stock via recipe consumption movements.

This is powerful, but it is also where duplicate or missing stock effects can happen if final ownership is not explicit.

## Buying Items Today

For a purchase invoice:

1. `do/doadd_invoice.php` classifies purchase type as incoming stock.
2. It writes `fat_details.qty_in = purchased_qty * u_val`.
3. It computes a moving-ish cost from `myitems.cost_price`, `myitems.itmqty`, and the new purchase unit price.
4. It updates `myitems.last_price` and `myitems.cost_price`.
5. The legacy trigger refreshes `myitems.itmqty`.

The legacy purchase invoice path can now shadow/bridge purchase rows through `InventoryInvoiceBridge`, and the new receiving surface posts purchase receipts through `InventoryPurchaseReceivingService`. The remaining migration risk is not the absence of a purchase ledger writer; it is proving when every legacy purchase entry path should be cut over to that writer and when old `fat_details` purchase stock truth can be retired.

## Opening Balance Today

`items_start_balance.php` displays a table with item code, item name, unit, editable new quantity/new price fields, current quantity/current price, and adjustment. For ingredients and packaging, if `inventory_item_balances` exists, it displays recipe-ledger `qty_on_hand` and moving average cost. Otherwise it falls back to `myitems.itmqty` and `myitems.cost_price`.

`save_start_balance.php`:

- calculates non-opening legacy quantity from `fat_details`,
- writes one opening row per item in `fat_details`,
- updates duplicate opening rows to deleted,
- refreshes `myitems.itmqty`/`cost_price` through `InventoryLegacyMirrorService`,
- if recipe tables exist, writes or updates one scoped `opening_balance` movement and upserts `inventory_item_balances`,
- if the Phase 3 metadata columns exist, stores `payload_hash` and `metadata_json` on that movement so reconciliation can distinguish the desired opening quantity, non-opening quantity, and opening adjustment.

The behavior is useful for migration, but it must not remain the final operator-facing stock-setting path without resolving type `14` and making movement ownership explicit.

## Final Ownership Recommendation

Future phases should make `RecipeInventoryMovementService` or a renamed general inventory service the single owner for stock-affecting movements. Legacy `fat_details` should remain an invoice/order detail table, not the inventory truth. `myitems.itmqty` should become a compatibility/read cache only during migration, then be removed from operator decisions.
