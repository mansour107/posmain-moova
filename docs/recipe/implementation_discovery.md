## 3. Migration Mechanism

The active additive schema mechanism is `classes/Sync/SchemaManager.php`, applied by `tools/run_migrations.php`.

Important behavior:

- Planned tables are returned from `SyncSchemaManager::plannedStatements()`.
- Existing tables are inspected through `INFORMATION_SCHEMA`.

Recipe schema must be added through this mechanism. Standalone SQL is not acceptable.

## 4. Tenant, Branch, And Store Identity

Live table evidence:

- `myitems` has `tenant int(11) DEFAULT 0`, `branch int(11) DEFAULT 0`.
- `fat_details` has `tenant int(11) DEFAULT 0`, `branch int(11) DEFAULT 0`.
- `ot_head` has `tenant int(11) DEFAULT 0`, `branch int(11) DEFAULT 0`.
- `item_availability` has `tenant INT NOT NULL DEFAULT 0`, `branch INT NOT NULL DEFAULT 0`.
- Sync tables use `pos_tenant INT`, `pos_branch INT`, and `branch_uuid CHAR(36)`.

Decision for recipe tables:

- Use integer branch identity.
- Use `pos_tenant INT NOT NULL DEFAULT 0`.
- Use `pos_branch INT NOT NULL DEFAULT 0`.
- Use `branch_uuid CHAR(36) NULL` only for sync/cloud correlation.
- Do not use `tenant VARCHAR(64)` or `branch VARCHAR(64)`.

Store/location evidence:

- `ot_head.store_id` exists and is nullable.
- `fat_details.det_store` exists and defaults to `1`.
- `settings.def_pos_store` exists.
- No obvious dedicated store/warehouse table was found in the quick live table scan.

Decision for recipe balance/cache/reservation tables:

- Use `store_id BIGINT UNSIGNED NOT NULL DEFAULT 0` where uniqueness depends on store/location.
- `0` means default branch store for the recipe ledger.
- Do not use nullable `store_id` in unique indexes.
- Active stock writes must resolve the real legacy store context before pilot consumption.

## 8. Accounting Gap

Evidence:

- `AccountingPostingService` currently posts table payment receipts.
- Procedural invoice flows also write `journal_heads` and `journal_entries` directly.
- `journal_heads` and `journal_entries` use legacy integer columns and account triggers.
- Live local inspection on 2026-05-23 showed `journal_entries.debit` and `journal_entries.credit` as `int(11)`, while recipe costs and ingredient quantities require decimal-safe posting.

Decision:

- Recipe COGS, production, waste, and refund accounting use `RecipeAccountingService`.
- `RecipeAccountingService` refuses to post if journal entry debit/credit columns are not decimal-safe, so ingredient costs cannot be silently rounded or truncated.
- Do not post recipe journals from endpoints.
- `SyncSchemaManager` now plans a non-destructive precision migration to widen legacy integer `journal_entries.debit` and `journal_entries.credit` to `DECIMAL(18,6)`.
- Active accounting remains blocked until that migration is reviewed/applied on the target deployment and account mappings are configured.

## 10. Final Plan Fixes Applied

The latest implementation must include these corrections:

- Recipe identity defaults are `0`, not `1`.
- `recipe_availability_cache` must include `order_type` and `channel` in the cache key.
- `external_order_line_map` uniqueness must be scoped by tenant/branch or branch UUID.
- Reservation movements must not change `qty_on_hand`; they affect `qty_reserved`.
- `store_id` must participate in stock/reservation idempotency keys or uniqueness.
