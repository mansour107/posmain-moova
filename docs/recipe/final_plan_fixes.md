# Final Recipe Plan Fixes

These fixes amend `POSMAIN_recipe_system_final_revised_plan_after_codex_review.txt` and are binding for implementation.

1. Recipe identity defaults must match POSMAIN's current schema shape: use `pos_tenant INT NOT NULL DEFAULT 0` and `pos_branch INT NOT NULL DEFAULT 0` unless later live discovery proves a different target.
2. `recipe_availability_cache` must include `order_type` and `channel`; the unique key must include `(pos_tenant, pos_branch, store_id, sellable_item_id, order_type, channel)`.
3. `external_order_line_map` uniqueness must include branch scope, such as `(pos_tenant, pos_branch, source_channel, external_order_id, external_line_id)`.
4. Reservation movement rows must not reduce `qty_on_hand`; reservations affect `qty_reserved` and availability only.
5. Stock/reservation idempotency must include `store_id` either in the deterministic key or in the relevant unique index.
6. Pilot `category_ids` must be enforced by runtime feature gates, not only readiness display. Category-only pilots fail closed unless the sellable item category is known and included; explicit pilot item IDs may still match when category is unknown.
7. Reservation writes must use the same pilot branch/item/category scope gate as consumption, accounting, availability, and menu sync. Outside-scope order lines must not create `recipe_order_line_usage`, `stock_reservations`, or reservation movements in pilot modes, including through direct reservation movement service calls; `full` mode remains the explicit broad rollout mode.
8. Recipe order-line usage idempotency must distinguish same-line quantity and modifier changes. Exact retries stay idempotent, but edits that keep the same POS detail id must create a new usage identity so old reservations can be released and the new quantity can be reserved.
9. Split payment must rebuild the original order's recipe reservation for the remaining quantity before the paid split child consumes stock. Direct paid lines must only decrement `qty_reserved` when active reservation rows exist for that same order line, so one paid line cannot steal another open order's reservation.
10. Table merge must transfer recipe reservation identity from source order to destination order. Merge should release source-order recipe usage/reservations and create destination-order usage/reservations for the moved lines without consuming stock; payment of the merged destination order then consumes exactly once.
11. Table merge recipe quantity reconstruction must use `RecipeDecimal`, including `qty_out - qty_in` divided by `u_val`; do not coerce recipe quantities through PHP floats while transferring reservations.
12. Table merge endpoints/services must call `RecipeOrderLifecycleService::onOrderMerged()` as the shared facade. The table merge service may collect source/destination line contexts, but it must not directly perform per-line cancellation/add lifecycle calls because that reintroduces endpoint/service-level recipe lifecycle bypasses.
13. Split payment services must call `RecipeOrderLifecycleService::onOrderSplit()` as the shared facade. The POS mutation service may calculate original/remaining/paid line contexts, but the source release, remaining reservation rebuild, and paid child consumption must be coordinated by the lifecycle facade.
14. Split payment recipe quantity reconstruction must use `RecipeDecimal`, including `(qty_out - qty_in) / u_val` and remaining-quantity calculations; do not coerce recipe reservation quantities through PHP floats while rebuilding original reservations.
15. Shared POS/table recipe contexts loaded from legacy `fat_details` must reconstruct lifecycle quantities with `RecipeDecimal`, including takeaway detail creation and table/order detail loading. Legacy totals/prices may still use existing float paths, but persisted recipe quantity inputs must not be derived by float division.
16. Moova/Cofe mapped recipe contexts must also reconstruct mapped lifecycle quantities with `RecipeDecimal`. Incoming external sell quantities may be normalized from payload values, but mapped legacy quantities such as `moova_pos_order_lines.qty_out / fat_details.u_val` must not be divided with PHP floats before reaching recipe lifecycle services.
17. Legacy cashier loaders that rehydrate editable POS/table rows must preserve `u_val` and present sell-unit quantity/price derived from `fat_details.qty_in`, `qty_out`, `u_val`, and unit price. They must not force `u_val=1` for existing rows, because that can turn one sell unit with a multi-unit conversion into multiple recipe lifecycle sell units during edit/save.
18. Branch-scoped pilot gates must fail closed when runtime scope is missing. If `POSMAIN_RECIPE_PILOT_POS_BRANCH` is set, active reservation, consumption, accounting, and availability gates require a resolved `RecipeScope` with the matching `pos_branch`; direct service callers must not activate recipe behavior with a null or unknown branch scope.
19. Accounting rollout readiness must require every recipe account used by the accounting service: COGS, raw inventory, prepared inventory, packaging inventory, waste expense, and production variance. A pilot must fail readiness before live accounting if any of those mappings are missing.
20. Recipe usage idempotency must prefer external `source_line_uuid` over local `order_line_uuid` and `fat_detail_id` when present. Moova/Cofe provider lines can share or merge into the same local POS detail during mapping; their provider line identity must remain distinct so replay protection does not collapse two real external lines into one recipe usage.
21. Active rollout evidence must separately prove realistic modifier substitution recipe setup and UI behavior. A generic recipe-management smoke is not enough for pilot/full readiness because additive and substitution modifiers have different stock and availability effects.
22. Active rollout evidence must include non-placeholder operator proof for production batches, waste/stock adjustments, paid refund/void reversal, and Moova/Cofe replay when recipe menu sync is enabled. Checklist ticks alone are not enough for these high-risk paths because each one crosses stock, accounting, audit, or external replay boundaries.
23. Active rollout evidence freshness must be validated from a content timestamp such as `Evidence completed at UTC`, not only from filesystem modification time. Touching or copying an old evidence file must not make it acceptable for active consumption/accounting/availability rollout.
24. Hosted/cloud or single-domain router recipe rollout must include separate hosted runtime schema evidence. Local `kody2` readiness is useful for development, but it must not approve active hosted consumption/accounting/availability unless the hosted/cloud runtime DBs or routed shop DBs have been verified too.
25. Active recipe Moova/menu sync must fail rollout readiness unless the underlying menu sync transport can actually publish. `POSMAIN_MENU_SYNC_ENABLED` must be on, and either sync outbox must be enabled or hosted cloud-to-branch publishing must be enabled for a cloud/fake-cloud runtime. Otherwise availability changes can be computed locally but never reach Moova/cloud menus.
26. Active recipe Moova/menu sync must also require recipe availability itself. Menu sync without `POSMAIN_RECIPE_AVAILABILITY` can publish ordinary item snapshots while omitting recipe-derived computed availability, so readiness must block that configuration instead of treating it as a valid recipe availability rollout.
27. Active recipe pilot evidence must treat `POSMAIN_ROLE=fake_cloud` as hosted/cloud scope. Sync publishers and cloud receivers already treat fake-cloud as cloud-like, so fake-cloud staging or test runtimes must provide hosted runtime schema evidence instead of passing from local-only `kody2` proof.
28. Runtime recipe Moova/menu sync gates must use the same dependency as readiness: `POSMAIN_RECIPE_MOOVA_SYNC` is not effectively enabled unless `POSMAIN_RECIPE_AVAILABILITY` is also enabled in `availability_pilot` or `full` mode. Readiness may still inspect the raw requested flag to produce a clear configuration blocker, but lifecycle/menu payload code must not emit recipe availability snapshots from a misconfigured flag combination.
29. If `POSMAIN_RECIPE_ALLOW_NEGATIVE_STOCK_WITH_APPROVAL=1` is enabled for an active pilot/full rollout, pilot evidence must separately prove the manager recipe stock override flow. Generic POS/table smoke is not enough because override approval crosses permissions, manager approval records, order mutation availability checks, and recipe audit logging.
30. `POSMAIN_RECIPE_STRICT_STOCK=1` must not be enabled together with `POSMAIN_RECIPE_ALLOW_NEGATIVE_STOCK_WITH_APPROVAL=1` for active rollout. Strict stock means insufficient ingredients are a hard stop; negative-stock approval means a manager can override insufficient ingredients. Readiness must block the contradiction before pilot operators see mixed UI and policy behavior.
31. `POSMAIN_RECIPE_ALLOW_NEGATIVE_STOCK_WITH_APPROVAL=1` must require `POSMAIN_RECIPE_AVAILABILITY=1` in `availability_pilot` or `full` rollout. The manager override flow is driven by computed recipe availability; without availability, the flag is misleading and no recipe-unavailable card can safely request the override.
32. Active recipe Moova/menu sync that relies on the branch `sync_outbox` must prove the branch outbox can actually deliver: branch role, branch UUID, cloud base URL, branch sync secret, branch sync enabled, and sync worker enabled. Otherwise readiness can pass before availability events are created, then those events sit pending forever and Moova/cloud menus never see the computed recipe availability.
33. Customer/Moova cost-leak masking must normalize payload key styles before checking sensitivity. Snake_case fields like `cost_price` and camelCase fields like `costPrice`, `unitCost`, `totalCost`, `ingredientCostJson`, or `internalCostPerSellUnit` all represent sensitive internal cost data and must be removed from public payloads unless an explicitly approved internal analytics flag is in force.
34. Production batch commits are active inventory writes and must not be enabled by `shadow`, `schema_only`, `read_only`, or `reserve_only` behavior. They require the active recipe consumption gate and must respect the same branch/item/category pilot scope as sale consumption before creating a draft, consuming inputs, creating output stock, or cancelling a draft batch.
35. Production batch accounting must be posted by `ProductionBatchService` inside the same transaction as production input/output movements. The production UI and mutation adapter may delegate to the production domain, but they must not call `RecipeAccountingService` directly. If journal posting fails in accounting-enabled mode, the input/output stock movements and batch commit must roll back together.
36. Production batch commits must refresh computed availability inside `ProductionBatchService` when recipe availability is active. The refresh must cover consumed input ingredients and the produced output item so direct make-to-order dependents, batch-prepared output availability, and recipes that use the prepared output are recalculated in the same transaction; endpoint/UI layers must not call `RecipeAvailabilityService` directly. Batch-prepared item availability must be based on prepared output stock on hand, not on how many additional batches raw ingredients could produce.
37. Batch-prepared sale consumption must consume the prepared output item stock, not the raw ingredient recipe lines. The raw recipe explosion remains available for production preview/commit and recipe cost calculation, but `RecipeExplosionService::explodeOrderLine()` for an active `batch_prepared` recipe must return a prepared-stock requirement for the sellable/output item. Sale COGS for that requirement must use the frozen recipe cost-per-sell-unit and credit the prepared inventory account when recipe accounting is active.
38. Batch-prepared return-to-stock refunds must restore prepared output stock and debit the prepared inventory account. The reversal accounting path must derive its inventory account type from the stored recipe usage explosion, so prepared-stock sales reverse against the same inventory class they credited at sale time.
39. Production yield variance policy must be explicit. The default policy may keep legacy-safe valuation by adjusting actual output unit cost, but when `production_variance_policy=post_variance` is configured, production commit must value output at planned unit cost, record a variance batch line, and let production accounting post the difference to the production variance account inside the same transaction.
40. Production yield variance policy must be runtime-configurable. Deployments should set `POSMAIN_RECIPE_PRODUCTION_VARIANCE_POLICY=adjust_unit_cost` for legacy-safe valuation or `POSMAIN_RECIPE_PRODUCTION_VARIANCE_POLICY=post_variance` when accountants want explicit production variance journals; invalid values must still fall back to `adjust_unit_cost`.
41. `POSMAIN_RECIPE_PRODUCTION_VARIANCE_POLICY=post_variance` must require active recipe accounting in rollout readiness. The policy intentionally creates a cost difference between production input and output movements; without accounting enabled in an accounting-capable mode, no production variance journal can balance that difference.
42. The operational dashboard must surface `production_variance_policy` and flag `production_variance_policy_requires_accounting`. Operators need to see the same production-variance misconfiguration that rollout readiness blocks, not only discover it from CLI output.
43. Active recipe modes must require their matching runtime flags in rollout readiness. `reserve_only` requires reservations, `consume_pilot` requires consumption, `accounting_pilot` requires consumption and accounting, and `availability_pilot`/`full` require availability. Otherwise operators can select an active-looking mode whose runtime gates remain no-op.
44. The operational dashboard must also surface active recipe mode/flag mismatches as `active_mode_flag_mismatches`. Operators should see when `full`, `availability_pilot`, `accounting_pilot`, `consume_pilot`, or `reserve_only` is selected but the matching runtime flags are still disabled.
45. Runtime preflight must also block active recipe mode/flag mismatches before browser/operator QA starts. `tools/recipe_runtime_preflight.php` should fail when `reserve_only`, `consume_pilot`, `accounting_pilot`, `availability_pilot`, or `full` is selected while the required runtime flags are still off.
46. The operational dashboard must surface `cost_public_payloads` and flag `public_cost_payloads_enabled`. Recipe cost exposure is blocked by rollout readiness unless an explicit override is supplied, so operators need the same risk visible on the dashboard.
47. The operational dashboard and runtime preflight must surface stock policy mismatches. Strict stock requires recipe availability, strict stock conflicts with manager negative-stock approval, and manager negative-stock approval requires recipe availability in active availability/full rollout.
48. Pilot modes must fail closed without an explicit pilot scope. `reserve_only`, `consume_pilot`, `accounting_pilot`, and `availability_pilot` require at least one configured pilot branch, item, or category before reservation, consumption, accounting, or availability gates can activate. `full` remains the only intentionally broad rollout mode.
49. `reserve_only` is an active write mode and must require fresh pilot evidence, but that evidence should be reservation-specific. It must prove schema/preflight/dashboard/reconciliation readiness, pilot fixture verification, reservation lifecycle QA, rollback readiness, and an isolated `recipe_reservation_lifecycle_runtime_test.php` proof without demanding production, waste, refund, accounting, or availability evidence that belongs to later modes.
50. Pilot evidence must follow effective mode gates, not raw environment flags alone. If `POSMAIN_RECIPE_ACCOUNTING=1`, `POSMAIN_RECIPE_AVAILABILITY=1`, `POSMAIN_RECIPE_MOOVA_SYNC=1`, or manager override flags are accidentally set in `reserve_only` or `consume_pilot`, the evidence template should not demand accounting, availability, Moova/menu sync, or manager override proof unless that behavior is actually effective for the selected mode.
51. `POSMAIN_RECIPE_STRICT_STOCK=1` must require effective recipe availability, not just a raw availability flag. If strict stock is configured in `read_only`, `shadow`, `reserve_only`, or `consume_pilot`, checkout availability enforcement is not active, so runtime preflight, rollout readiness, and the operational dashboard must block or surface `strict_stock_requires_effective_recipe_availability` instead of letting operators believe strict ingredient blocking is live.
